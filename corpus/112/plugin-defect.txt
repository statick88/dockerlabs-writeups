          }
          if( !isset($_POST['sed_page_ajax']) || $_POST['sed_page_ajax'] !=  $ajax){
              $this->sed_die( -2 );
          }
  }

MY OWN INSTRUMENTS THAT LIED ABOUT THIS, AND WHAT CAUGHT THEM
================================================================================

A Perl path resolver I wrote to enumerate every dirname(__FILE__)-relative
require/include printed, three consecutive times, with exit 0 and clean output:

    call sites examined: 0
    targets present:     0
    targets MISSING:     0

It had found nothing because it looked in the wrong place. Three wrong regexes,
each plausible on a glance:

  1. \b(?:require|require_once)\s*\( — assumed require is always followed by a
     parenthesis. It is not: `require_once dirname( __FILE__ )` has no wrapping
     parenthesis, so the pattern matched nothing at all.
  2. \(([^;]*)\; — after fixing the above, required a closing ")" before ";",
     which the parenthesis-less form does not have.
  3. A shell sed extraction of the path literal that did not strip the leading
     quote. It reported 57 targets missing when at most a handful were, and
     named /var/www/html/wp-content/plugins/site-editor/includes/app_file.class.php
     as absent — a file whose directory listing I had already read earlier in
     the same session.

WHAT CAUGHT IT: I did not accept the 57, because it contradicted a directory
listing I already held. Cross-check the sweep against an artefact you already
fetched.

FIX: stop parsing PHP with regex. Rewritten with token_get_all(). That version
then reported honestly (call sites: 54, resolved: 0, unparsed: 54) and revealed
the real reason: dirname tokenises as T_STRING, not T_DIR. T_DIR is the __DIR__
magic CONSTANT — a different thing with a confusingly similar name. A third
wrong answer, structurally correct, and still wrong.

RULE ADDED: a count of zero from an instrument you wrote today is a statement
about the instrument until proven otherwise.
