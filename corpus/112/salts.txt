THE TRAP THIS AVOIDS. wp-config.php:51-58 ships all eight auth keys as the
installer placeholder:

  51: define( 'AUTH_KEY',         'put your unique phrase here' );
  52: define( 'SECURE_AUTH_KEY',  'put your unique phrase here' );
  53: define( 'LOGGED_IN_KEY',    'put your unique phrase here' );
  54: define( 'NONCE_KEY',        'put your unique phrase here' );
  55: define( 'AUTH_SALT',        'put your unique phrase here' );
  56: define( 'SECURE_AUTH_SALT', 'put your unique phrase here' );
  57: define( 'LOGGED_IN_SALT',   'put your unique phrase here' );
  58: define( 'NONCE_SALT',       'put your unique phrase here' );

A document that reads that and concludes "the auth cookie is forgeable because
AUTH_KEY is a placeholder" is the corpus's own retracted finding. So the
framework was asked, not the file.

CONCLUSION, FROM MEASUREMENT: the framework IGNORES the wp-config.php
placeholder and consumes the 64+64 characters stored in wp_options.
`defined('AUTH_KEY')` is trivially true of any constant and says nothing about
which value is used.

THE MECHANISM, from this image's own pluggable.php

pluggable.php:2442 — the placeholder is pre-seeded into a skip-list:

  static $duplicated_keys;
  if ( null === $duplicated_keys ) {
      $duplicated_keys = array(
          'put your unique phrase here' => true,
      );

pluggable.php:2477 — the constant is only taken when the skip-list lacks it:

  if ( defined( $const ) && constant( $const ) && empty( $duplicated_keys[ constant( $const ) ] ) ) {
      $values[ $type ] = constant( $const );
  } elseif ( ! $values[ $type ] ) {
      $values[ $type ] = get_site_option( "{$scheme}_{$type}" );

With the placeholder present, the first branch is false and it falls through to
get_site_option().

================================================================================
MY OWN WRONG INTERMEDIATE CONCLUSION, AND THE COUNT THAT CORRECTED IT
================================================================================

On first reading Measurement 1 I assumed there were NO auth_key/auth_salt rows in
wp_options — my earlier option dump had filtered out rows I did not recognise —
and concluded "wp_salt() generates a random value per boot, so a database read is
harmless".

I then counted instead of assuming:

  SELECT COUNT(*) FROM wp_options
   WHERE option_name IN ('auth_key','auth_salt','secure_auth_key','secure_auth_salt',
                         'logged_in_key','logged_in_salt','nonce_key','nonce_salt');
  -> 8

(SELECT COUNT(*) FROM wp_options -> 172 total rows.)

The count was 8, not 0, and wp_salt('auth') is exactly the concatenation of two
of them. My first conclusion was wrong in a way that would have produced a
correct-sounding but wrong security note. The count changed the finding.

CLAIMED, from measurement: the WordPress cookie salts in this image are real
random 64+64 character values stored in wp_options; the wp-config.php
placeholder is skipped. A finding asserting that the placeholder makes the
cookie forgeable is REFUTED for this image.

any SQL injection or database read discloses them.
