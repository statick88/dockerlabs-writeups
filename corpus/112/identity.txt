112 Asucar — identity evidence
Every predicate below is evaluated AS the identity it is about, via
`setpriv --reuid=<user> --regid=<user> --init-groups`.
Never through `docker exec` (which is root and would observe itself, not the
boundary). Never with a root-run `test -w`.

================================================================================
THE FACTS BEHIND THOSE ANSWERS, from the artefact
================================================================================

$ getent group curiosito
curiosito:x:1000:www-data

$ stat -c "%a %U:%G %n" /home/curiosito/.ssh/id_rsa /home/curiosito/.ssh/authorized_keys /home/curiosito
250 curiosito:curiosito /home/curiosito/.ssh/id_rsa
654 curiosito:www-data /home/curiosito/.ssh/authorized_keys
755 curiosito:curiosito /home/curiosito

`654` decodes as owner rw-, group r-x, other r--. The group bits are 5, not 6:
www-data can READ authorized_keys and cannot WRITE it. Reading `654` as
"group www-data can write" would have been a wrong mechanism.

$ stat -c "%a %U:%G %n" /home/curiosito/.ssh
250 curiosito:curiosito /home/curiosito/.ssh
   (d-wxr-x--- : owner w, group r-x, other ---)
Group curiosito = r-x, so www-data can traverse and list, and that is exactly
why it can reach id_rsa.

$ cat /home/curiosito/.bash_history
cd
ssh-keygen -t rsa -b 4096
ls
cd /.ssh
ls
ls -la
cd.ssh
cd .ssh
ls
cat id_rsa.pub >> ~/.ssh/authorized_keys
ls
rm id_rsa.pub
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
chmod 644 ~/.ssh/authorized_keys
chmod 700 ~/.ssh
sudo usermod -a -G curiosito www-data
pwd
sudo chown curiosito:www-data /home/curiosito/.ssh/authorized_keys
sudo su
passwd root
exit

The two `sudo` lines are the setup for the group membership above.

$ cat /etc/sudoers | tail -4
# User privilege specification
root	ALL=(ALL:ALL) ALL

# Allow members of group sudo to execute any command
%sudo	ALL=(ALL:ALL) ALL

@includedir /etc/sudoers.d
curiosito ALL=(root) NOPASSWD: /usr/bin/puttygen

Note: NO wildcard. The `sudo --help` argument-splitting bypass (uid=-1) does
NOT apply to this line.

--- /root/.mysql_history, and why the credential in it is still protected ---
$ ls -la /root/.mysql_history
-rw-r--r-- 1 root root 885 May 12  2024 /root/.mysql_history
$ ls -ld /root
drwx------ 1 root root 4096 Sep 30 08:53 /root

$ grep -n "curiosito" /root/.mysql_history
CREATE USER 'curiosito'@'%' IDENTIFIED BY 'password++321dcbsodivbfva';
GRANT ALL PRIVILEGES ON wordpress.* TO 'curiosito'@'%';

The file is mode 644 and contains a live database password, but /root is mode
700, so www-data cannot traverse to it (measured: Permission denied, above).
The mode of the history file is still a defect worth fixing; the boundary that
actually protects it is /root's own mode.
