STEP 1 — PROVE THE ORACLE CAN FIRE, BEFORE BELIEVING ANY NEGATIVE
================================================================================

So a throwaway account with a known password was inserted, and the oracle was

================================================================================
STEP 3 — THE SWEEP, WITH ITS WORK COUNT
================================================================================

Method: system.multicall, batches of 500, one wp.getUsersBlogs call per
candidate, user `wordpress`. A batch counts as a hit only if the response
contains <name>isAdmin</name>; the hit is then mapped back to its candidate.

Candidate sources:
  * a hand-built list from the artefact's own content (blogname "Asucar Moreno",
    "Mariscos Recio", "Antonio Recio Mata", "Mairena del Alcor", "Firulais",
    the vhost name asucar.dl, the DB password SUPERPASSWORD, the login name
    itself, and numeric/leet/year permutations of each)
  * ~/PenTestMethodology/wordlists/Passwords.txt, filtered to
    length 4-16 (517506 lines in, 408778 candidates after filtering)
  * union

Small batches, before the big list, for fast feedback:
    batch 1:  22 candidates, 22 faultCode, 22 x "Nombre de usuario o contraseña incorrectos."
    batch 2:  34 candidates, 34 faultCode, 34 x the same single fault string
    batch 3: 175 candidates, 175 faultCode, 175 x the same single fault string
              (0 occurrences of isAdmin)

Full sweep:
    candidates tested : 409165
    hits              : None
    distinct fault strings in the responses: 1
      "Nombre de usuario o contraseña incorrectos."

Every batch used the SAME single fault string, and no batch returned
`isAdmin`. Given that the positive control in Step 1 returned `isAdmin` on the
same endpoint in the same session, this is a measured negative, not an
untested one.

================================================================================
WHAT THIS NEGATIVE DOES AND DOES NOT COVER
================================================================================

COVERES: the password for `wordpress` is not in a 409,165-entry dictionary
         sweep, is not the site content, is not the database password, and is
         not the MySQL password found in /root/.mysql_history
         ('password++321dcbsodivbfva' — tested explicitly).

DOES NOT COVER: a non-dictionary password; a password from a source outside this
         corpus; a password derivable from something I did not find.

Note on the latter: /root/.mysql_history is mode 644 and contains
  CREATE USER 'curiosito'@'%' IDENTIFIED BY 'password++321dcbsodivbfva';
That is a DATABASE credential for a MySQL account, and /root is mode 700, so
www-data cannot reach it (measured: Permission denied). It is not a WordPress
password and it is not curiosito's OS password. Both were tested against
wp.getUsersBlogs and both failed.
